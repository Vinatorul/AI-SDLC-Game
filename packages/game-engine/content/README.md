# Сценарии игры

Основной технический сценарий лежит в `scenarios/technical-mvp.json`. Здесь можно менять тексты,
доступные ходы, события, численные эффекты и правила игры. После изменения проверьте файл:

```bash
pnpm scenario:validate packages/game-engine/content/scenarios/technical-mvp.json
pnpm copy:validate
```

Некорректный файл не запустится. Проверка ловит лишние поля, неизвестные этапы и свойства,
повторяющиеся идентификаторы, неправильные ссылки и расхождение числа раундов с `roundLimit`.
`copy:validate` ловит известные проблемы в структуре и формулировках, но не умеет отличать живой
текст от формально правильного. После него всё равно нужна ручная редактура.

## Как устроен ход

В каждом ходу проходят два голосования:

1. Игроки выбирают этап из списка `rounds[].stageChoices`. В основном сценарии доступны все восемь.
2. Игроки выбирают действие из `actionIds` победившего этапа.

Сами действия лежат один раз в общем каталоге `stageActions`. Шаблон хода только ссылается на
них по стабильному идентификатору. К уже изменённому этапу можно вернуться и применить другое
действие.

`rules.roundMode` задаёт, как используется список `rounds`:

- `FINITE` — список проходит один раз, затем игра проверяет условие победы;
- `CYCLIC` — шаблоны используются повторно, а игра продолжается до победы или критического
  значения метрики.

В циклическом режиме каждый повтор создаёт новый ход со своими голосами и последствиями.
`roundLimit` в обоих режимах должен совпадать с числом шаблонов в `rounds`. В основном
сценарии шаблон один: порядок событий задаёт не номер хода, а выбранное действие и история игры.

У действия есть:

- `stage` — этап SDLC;
- `title`, `description`, `evidence` и `shortFeedback` — видимый текст;
- `effect` и `addProperties` — последствия первого применения для метрик и свойств процесса;
- `effectReasons` — отдельное объяснение каждой ненулевой поправки из `effect` для ведущего;
- `repeatEffect` и `repeatEffectReasons` — необязательные последствия повторного применения;
- `activationRequirements` — конкретные действия, без которых установленный AI-инструмент ещё не
  считается рабочим;
- `availableInStates` — состояния этапа, в которых действие доступно;
- `resultingStageState` или `stageTransitions` — состояние этапа после решения;
- `repeatable` — можно ли применять то же действие повторно.

Укажите ровно один способ перехода. `resultingStageState` подходит, когда результат одинаков из
любого текущего состояния. `stageTransitions` нужен, когда действие по-разному работает на сером,
зелёном и сломанном этапе. В нём обязательно перечислите все три состояния, даже если в одном из
них действие недоступно:

```json
"availableInStates": ["AS_IS", "AI_ENABLED", "BROKEN"],
"stageTransitions": {
  "AS_IS": "AS_IS",
  "AI_ENABLED": "AI_ENABLED",
  "BROKEN": "AS_IS"
}
```

Так обычно работает повторяемое улучшение процесса или подготовка основы: на сером этапе оно
готовит почву, на зелёном не отключает уже работающий AI, а сломанный этап чинит до обычного
рабочего состояния. Само по себе такое действие не выдаётся за AI-внедрение.

По умолчанию ставьте `repeatable: false`. Если действие разрешено повторять, его обычный `effect`
применяется только в первый раз, а следующий выбор численно нейтрален. Добавляйте `repeatEffect`
только тогда, когда каждый повтор действительно создаёт новый измеримый результат. Подготовку
основы обычно делайте повторяемой и оставляйте без `repeatEffect`: польза придёт через ремонт этапа,
новое свойство процесса или более безопасное событие в следующем ходу. История уже применённых
действий сохраняется отдельно от текущего состояния этапа.

Поле `key` — короткая метка на карточке. У действий, которые могут оказаться в одном голосовании,
метки должны различаться. Порядок `actionIds` задаёт порядок карточек.

Состояние этапа описывает реальную работу, а не тип технологии:

- `AI_ENABLED` — AI уже выполняет заметную задачу на этом этапе. Stage-specific MCP, skill, база
  знаний или граф зависимостей тоже могут сделать кубик зелёным, если через них AI действительно
  работает, а не просто получил заготовку на будущее;
- `AS_IS` — команда укрепила процесс или подготовила данные и инструменты, но AI ещё не участвует
  в работе этапа. Такой ход может починить `BROKEN` до `AS_IS`, не выдавая ремонт за AI-внедрение;
- `BROKEN` — выбранный подход сделал этап ненадёжным или нерабочим.

Инфраструктурное действие кладите в тот кубик, работу которого оно меняет. MCP для живого контура
деплоя относится к деплою, а skill для генерации автотестов — к тестированию. Не складывайте все
MCP, skills и базы знаний в техническую проработку только потому, что это инфраструктура.

Само наличие артефакта ещё ничего не доказывает. Skill может генерировать полезные тесты, а может
размножать проверки, которые ничего не ловят. MCP может дать AI рабочий контур деплоя, а может
открыть пару бесполезных команд. Проверяйте основу через `hasProperty`, `missingProperty`, историю
действий и состояния соседних этапов. Действие может сначала предложить `AI_ENABLED`, а событие при
недостающей основе переопределит этап в `AS_IS` или `BROKEN`. Если игроки должны подготовить основу
и попробовать ещё раз, оставьте действие повторяемым.

Общее свойство используйте только тогда, когда любой способ его получить действительно закрывает
зависимость. Если AI нужен конкретный граф, конкретный skill или MCP для деплоя, проверяйте
`hasAppliedActions` и `missingAppliedActions`, а не подменяйте эту зависимость широким
`currentContext` или `observability`. Иначе база продуктовых решений сможет случайно заменить граф
зависимостей, а бизнес-метрики — данные о состоянии сервиса после релиза.

Когда команда позже добавляет недостающую основу, движок повторно проверяет
`activationRequirements`. Если ранняя установка безопасно оставила этап в `AS_IS`, готовый
AI-инструмент включается и переводит этап в `AI_ENABLED`. Одна основа может включить сразу несколько
инструментов в соседних кубиках. Если ранняя попытка действительно сделала этап ненадёжным и
оставила его в `BROKEN`, поздняя основа не чинит его автоматически: нужно выбрать ремонт или
повторить внедрение. Для каждого порядка добавляйте отдельный фокусный тест.

В заголовке AI-действия назовите конкретную работу AI. Решение или проверку человека укажите там
же или в первом предложении. Для обычной инженерной практики прямо назовите, что делает команда,
и поясните, что AI пока не встроен. Финальная карта использует эти же заголовки, поэтому одна лишь
установка инструмента не должна автоматически делать кубик зелёным.

## Как писать текст

Все поля, которые видят игроки и ведущий, пишите на разговорном русском. В каждой формулировке
должно быть понятно: кто что сделал или проверил и к чему это привело на практике. Заголовок
действия называет реальный выбор. Описание уточняет работу AI, границу решения человека и важные
условия. Событие говорит, что конкретно произошло. `shortFeedback` объясняет цену или пользу
выбора, а не повторяет заголовок.

Не подменяйте причину пересказом метрики: «качество выросло», «управляемость снизилась» или
«получили положительный эффект» ничего не объясняют. Не пишите в видимом тексте про цвет кубика.
Убирайте корпоративные обороты, общие слова про AI и термины, за которыми не видно действия. Если
важны MCP, скилл, агент или база знаний, напишите, к каким данным или командам они дают доступ, кто
проверяет результат и что именно не сработает без нужной основы.

Первый технически верный вариант считайте черновиком. Перепишите его так, как ведущий сказал бы
эту мысль вслух, затем прочитайте вслух ещё раз. Если фраза звучит как аналитическая записка,
документация или сгенерированный текст, перепишите её. `pnpm copy:validate` — только страховка от
известных проблем. Успешная команда не заменяет ручную редактуру и проверку вслух.

В видимом тексте используйте **релиз**, а не «выпуск», и **откат**, а не «возврат прошлой версии».
Слово «восстановление» оставляйте для восстановления сервиса или состояния игры, когда речь не
идёт об откате версии.

Говорите **метрика**, а не «показатель», и **прод**, а не `production` или «боевое окружение».
**Баг** — дефект в коде или поведении продукта. **Инцидент** — ситуация в проде, которую команда
разбирает и устраняет. Не называйте их «ошибкой» или «сбоем». **Автотест** — тест, который
запускается автоматически; **тест** — сам сценарий или код теста; **проверка** — более широкое
действие человека или инструмента, например сборка, линтер, тесты и ручная сверка результата.

### Почему изменились метрики

У каждого действия и события рядом с `effect` должен быть `effectReasons`. Для каждой ненулевой
метрики укажите одну отдельную причину; набор ключей должен в точности совпадать с ненулевыми
ключами `effect`:

```json
"effect": {
  "quality": -2,
  "teamCapacity": -1
},
"effectReasons": {
  "quality": "AI пропустил изменение контракта, и баг дошёл до следующего этапа.",
  "teamCapacity": "Команде пришлось вручную разбирать и переделывать изменение."
}
```

`effectReasons` — единственный источник текста, которым интерфейс объясняет ведущему численное
изменение. Не рассчитывайте, что интерфейс догадается о причине по знаку, названию метрики,
`description` или `shortFeedback`. Одна причина объясняет одну метрику и называет механизм: какая
работа ускорилась, что пришлось переделать, какой баг поймали или почему команда потеряла
контроль. Для нулевого или отсутствующего эффекта причину не добавляйте.

Для постоянных поправок работает то же правило: `propertyEffectReasons` объясняет
`propertyEffects`, а `stageStateEffectReasons` — `stageStateEffects`. Текст пишется в сценарии,
а не выдумывается интерфейсом.

## События и накопленный контекст

`eventRules` проверяются сверху вниз. Последнее правило всегда безусловное и служит резервным.
Условия смотрят на выбранное действие и накопленное состояние:

- `actionIds` — выбранное действие текущего хода;
- `hasProperty` и `missingProperty` — свойства процесса;
- `hasResultingProperty` и `missingResultingProperty` — свойства с учётом того, что добавляет
  текущее действие;
- `hasAppliedActions` — все перечисленные действия должны быть в предыдущих ходах;
- `missingAppliedActions` — ни одного из перечисленных действий не должно быть в предыдущих ходах;
- `appliedActionCount` — общее число предыдущих действий, границы задаются через `minimum` и
  `maximum`;
- `appliedActionCounts` — число предыдущих действий из конкретного списка `actionIds`;
- `stageStates` — текущие состояния этапов;
- `stageActionCounts` — число предыдущих действий по конкретному этапу;
- `stageActionCountsSinceLast` — число действий одного этапа после последнего действия другого;
  необязательный `actionIds` оставляет в подсчёте только перечисленные действия этого этапа.
  Используйте фильтр, если подготовка на том же этапе не должна считаться выполненной работой:
  например, настройка команд CI не должна увеличивать число написанных изменений.

Все условия одного правила должны выполниться одновременно. Так события можно связывать с
предыдущими решениями, не перечисляя отдельную ветку для каждой комбинации.

Если событие ломает этап, в `title` и `description` нужно назвать конкретную причину: например,
поток изменений превысил возможности ревью и QA. Каждая отрицательная причина в `effectReasons`
должна связать тот же механизм со своей метрикой. Фразы вроде «этап сломан, поэтому TTM снизился»
не подходят: они называют состояние, но не объясняют, откуда оно взялось. Если событие говорит о
накопившейся очереди, условие должно требовать несколько соответствующих действий в истории.

Если AI-инструмент пока нельзя безопасно включить, но команда остановилась и продолжила работать
по старому ручному процессу, оставляйте этап в `AS_IS`. Состояние `BROKEN` подходит только для
случая, когда этап действительно стал ненадёжным или перестал работать.

Событие может добавить или удалить свойства через `addProperties` и `removeProperties`. Используйте
это, когда полезный результат становится известен только после события. Например, AI-действие не
должно сразу добавлять `automatedTests`: успешное событие добавит свойство, а неудачное просто его
не добавит. Удаляйте уже полученное свойство только тогда, когда событие действительно сделало его
непригодным. Обычный `event.effect` применяется только при первом выборе действия. Для повторного
измеримого результата задайте `event.repeatEffect` и `event.repeatEffectReasons`; без них повторное
событие численно нейтрально.

## Остальная конфигурация

- `rules` — режим ходов, число шаблонов, пороги, порядок решений и условие победы;
- `rules.shuffleActionChoices` — перемешивать ли решения при создании второго голосования. Один
  порядок сохраняется в бюллетене и одинаков для всех экранов;
- `mechanics.initialMetrics` — стартовые значения четырёх метрик;
- `mechanics.metricBounds` — нижняя и верхняя границы метрик;
- `mechanics.metricDefinitions` — видимые названия, короткий смысл, подписи и описания крайних
  значений;
- `mechanics.metricScaleDescription` — общая подсказка над метриками;
- `mechanics.positiveEffectRequirements` — этапы, которые должны работать, чтобы положительный
  эффект решения или события был засчитан. `requireActionStage` проверяет выбранный этап, а
  `additionalStages` задаёт дополнительные зависимости отдельно для каждой метрики и исходного
  этапа;
- `mechanics.propertyEffects` — постоянные поправки приобретённых свойств процесса. В основном
  сценарии они пустые: свойства защищают от связанных событий, но не начисляют очки каждый ход;
- `mechanics.stageStateEffects` — поправки за итоговое состояние каждого этапа после текущего
  решения и события;
- `rounds[].title` и `rounds[].situation` — заголовок и вопрос хода;
- `event.effect` и `event.stageChanges` — последствия выбранного события.
- `stageActions.*.activationRequirements` — связи AI-инструментов с конкретными основами в этом или
  соседних этапах.

В сценариях версии 3 и выше все метрики направлены одинаково: больше — лучше. Основная шкала идёт от
−10 до +10 и начинается с 0. Ноль должен находиться внутри `metricBounds`: интерфейс рисует
ухудшение влево от него, а улучшение — вправо. Порог опасной зоны — −5, критической — −8. Эти
значения задаются в `mechanics` и `rules`, поэтому другой сценарий может выбрать свои границы.

Стабильные технические идентификаторы метрик не нужно показывать игрокам:

- `deliverySpeed` — TTM;
- `controllability` — предсказуемость результата;
- `teamCapacity` — баланс Run / Change;
- `quality` — качество и стабильность.

Названия и пояснения берутся из `metricDefinitions`, а не из кода фронтенда. При настройке
эффектов используйте целые баллы: 1 — небольшой эффект, 2 — заметный, 3 — сильный. Допустимые
свойства: `humanReview`, `automatedTests`, `currentContext`, `observability`, `rollback`. Допустимые
состояния этапа: `AS_IS`, `AI_ENABLED`, `BROKEN`.

В основном сценарии `stageStateEffects` пусты: состояние этапа не меняет метрики в каждом
следующем ходу. `BROKEN` остаётся препятствием для победы, а непосредственный ущерб задаётся в
событии, которое сломало этап. Другой сценарий может добавить постоянную поправку вместе с точным
объяснением в `stageStateEffectReasons`.

Положительный эффект решения и события проверяется по итоговому состоянию этапов в этом же ходу.
Если действие починило нужный этап, плюс можно получить. Если событие сломало его, плюс не
засчитывается, а минусы остаются. Для TTM основной сценарий проверяет не только выбранный этап, но
и оставшийся путь до деплоя. Например, техническая проработка не ускорит TTM, пока написание кода
сломано. Ведущий увидит, какой бонус не сработал и какой этап его остановил.

`evidence: "FACT"` используйте только для проверенного наблюдения. Игровые допущения и
непроверенные последствия помечайте как `"SCENARIO"`.

## Как добавить действие или событие

1. Добавьте действие в `stageActions` под новым стабильным идентификатором.
2. Укажите этот идентификатор в `actionIds` нужного этапа в шаблоне хода.
3. Добавьте для него условное или обычное событие перед резервным правилом.
4. В основном сценарии оставьте все восемь этапов и проверьте, что они доступны даже после
   повторных решений.
5. Для `CYCLIC` оставьте у каждого этапа хотя бы одно осмысленное повторяемое действие.
6. Обновите `version`, запустите `pnpm scenario:validate <путь>` и `pnpm copy:validate`, затем
   вручную прочитайте вслух все изменённые видимые строки.
7. Запустите узкие тесты движка для изменённых условий и последствий.

## Новый сценарий

1. Скопируйте существующий JSON в новый файл в `scenarios`.
2. Задайте новый стабильный `id`, начните `version` с 1, сохраните `schemaVersion: 4` и
   отредактируйте содержимое.
3. Проверьте файл командой `pnpm scenario:validate <путь>`.
4. Запустите API с абсолютным путём в `SCENARIO_PATH`.

```bash
SCENARIO_PATH="$PWD/packages/game-engine/content/scenarios/my-scenario.json" pnpm dev:api
```

В Docker файл можно подключить без пересборки образа:

```bash
docker run --rm -p 8787:8787 \
  -e SCENARIO_PATH=/config/scenario.json \
  -v "$PWD/my-scenario.json:/config/scenario.json:ro" \
  -v ai-sdlc-data:/data ai-sdlc-api
```

После изменения внешнего файла перезапустите API. Новые комнаты получат новый сценарий, а уже
созданные продолжат использовать сохранённый в SQLite снимок.
