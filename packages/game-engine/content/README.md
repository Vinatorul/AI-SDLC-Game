# Сценарии игры

Основной технический сценарий лежит в `scenarios/technical-mvp.json`. Здесь можно менять тексты,
доступные ходы, события, численные эффекты и правила игры. После изменения проверьте файл:

```bash
pnpm scenario:validate packages/game-engine/content/scenarios/technical-mvp.json
```

Некорректный файл не запустится. Проверка ловит лишние поля, неизвестные этапы и свойства,
повторяющиеся идентификаторы, неправильные ссылки и расхождение числа раундов с `roundLimit`.

## Как устроен ход

В каждом ходу проходят два голосования:

1. Игроки выбирают этап из списка `rounds[].stageChoices`. В основном сценарии доступны все восемь.
2. Игроки выбирают действие из `actionIds` победившего этапа.

Сами действия лежат один раз в общем каталоге `stageActions`. Шаблон хода только ссылается на
них по стабильному идентификатору. К уже изменённому этапу можно вернуться и применить другое
действие.

`rules.roundMode` задаёт, как используется список `rounds`:

- `FINITE` — список проходит один раз, затем игра проверяет условие победы;
- `CYCLIC` — шаблоны используются повторно, а игра продолжается до победы или критического
  значения показателя.

В циклическом режиме каждый повтор создаёт новый ход со своими голосами и последствиями.
`roundLimit` в обоих режимах должен совпадать с числом шаблонов в `rounds`. В основном
сценарии шаблон один: порядок событий задаёт не номер хода, а выбранное действие и история игры.

У действия есть:

- `stage` — этап SDLC;
- `title`, `description`, `evidence` и `shortFeedback` — видимый текст;
- `effect` и `addProperties` — последствия для показателей и свойств процесса;
- `availableInStates` — состояния этапа, в которых действие доступно;
- `resultingStageState` — состояние этапа после решения;
- `repeatable` — можно ли применять то же действие повторно.

По умолчанию ставьте `repeatable: false`: повторяемое действие снова применяет свой численный
эффект. Если этап должен оставаться доступным всю игру, оставьте для него хотя бы одно осмысленное
повторяемое действие во всех трёх состояниях. Чтобы починить сломанный этап, разрешите действие в
состоянии `BROKEN` и задайте `resultingStageState: "AI_ENABLED"`. История уже применённых действий
сохраняется отдельно от текущего состояния этапа.

Поле `key` — короткая метка на карточке. У действий, которые могут оказаться в одном голосовании,
метки должны различаться. Порядок `actionIds` задаёт порядок карточек.

Заголовок действия должен сразу отвечать на два вопроса: что делает AI и что проверяет или решает
человек. Если действие автономное, это тоже должно быть видно без открытия подробного описания.
Финальная карта использует эти же заголовки, чтобы показать новое разделение работы по этапам.

## События и накопленный контекст

`eventRules` проверяются сверху вниз. Последнее правило всегда безусловное и служит резервным.
Условия смотрят на выбранное действие и накопленное состояние:

- `actionIds` — выбранное действие текущего хода;
- `hasProperty` и `missingProperty` — свойства процесса;
- `hasResultingProperty` и `missingResultingProperty` — свойства с учётом того, что добавляет
  текущее действие;
- `hasAppliedActions` и `missingAppliedActions` — действия из предыдущих ходов;
- `appliedActionCount` — общее число предыдущих действий, границы задаются через `minimum` и
  `maximum`;
- `stageStates` — текущие состояния этапов;
- `stageActionCounts` — число предыдущих действий по конкретному этапу.

Все условия одного правила должны выполниться одновременно. Так события можно связывать с
предыдущими решениями, не перечисляя отдельную ветку для каждой комбинации.

## Остальная конфигурация

- `rules` — режим ходов, число шаблонов, пороги и условие победы;
- `mechanics.initialMetrics` — стартовые значения четырёх показателей;
- `mechanics.metricBounds` — нижняя и верхняя границы показателей;
- `mechanics.metricDefinitions` — видимые названия, короткий смысл, подписи и описания крайних
  значений;
- `mechanics.metricScaleDescription` — общая подсказка над показателями;
- `mechanics.propertyEffects` — постоянные поправки приобретённых свойств процесса. В основном
  сценарии они пустые: свойства защищают от связанных событий, но не начисляют очки каждый ход;
- `mechanics.stageStateEffects` — поправки за итоговое состояние каждого этапа после текущего
  решения и события;
- `rounds[].title` и `rounds[].situation` — заголовок и вопрос хода;
- `event.effect` и `event.stageChanges` — последствия выбранного события.

В сценарии версии 3 все показатели направлены одинаково: больше — лучше. Основная шкала идёт от
−10 до +10 и начинается с 0. Ноль должен находиться внутри `metricBounds`: интерфейс рисует
ухудшение влево от него, а улучшение — вправо. Порог опасной зоны — −5, критической — −8. Эти
значения задаются в `mechanics` и `rules`, поэтому другой сценарий может выбрать свои границы.

Стабильные технические идентификаторы показателей не нужно показывать игрокам:

- `deliverySpeed` — TTM;
- `controllability` — предсказуемость результата;
- `teamCapacity` — баланс Run / Change;
- `quality` — качество и стабильность.

Названия и пояснения берутся из `metricDefinitions`, а не из кода фронтенда. При настройке
эффектов используйте целые баллы: 1 — небольшой эффект, 2 — заметный, 3 — сильный. Допустимые
свойства: `humanReview`, `automatedTests`, `currentContext`, `observability`, `rollback`. Допустимые
состояния этапа: `AS_IS`, `AI_ENABLED`, `BROKEN`.

В основном сценарии каждый `BROKEN`-этап уменьшает TTM на 1 балл за ход, пока этап не починят.
Этот штраф задаётся в `mechanics.stageStateEffects`, а не в движке. Сначала движок получает
итоговую карту этапов, поэтому новый сломанный этап влияет на тот же ход, а починенный — уже нет.

`evidence: "FACT"` используйте только для проверенного наблюдения. Игровые допущения и
непроверенные последствия помечайте как `"SCENARIO"`.

## Как добавить действие или событие

1. Добавьте действие в `stageActions` под новым стабильным идентификатором.
2. Укажите этот идентификатор в `actionIds` нужного этапа в шаблоне хода.
3. Добавьте для него условное или обычное событие перед резервным правилом.
4. В основном сценарии оставьте все восемь этапов и проверьте, что они доступны даже после
   повторных решений.
5. Для `CYCLIC` оставьте у каждого этапа хотя бы одно осмысленное повторяемое действие.
6. Обновите `version` и запустите проверку сценария и узкие тесты движка.

## Новый сценарий

1. Скопируйте существующий JSON в новый файл в `scenarios`.
2. Задайте новый стабильный `id`, начните `version` с 1, сохраните `schemaVersion: 3` и
   отредактируйте содержимое.
3. Проверьте файл командой `pnpm scenario:validate <путь>`.
4. Запустите API с абсолютным путём в `SCENARIO_PATH`.

```bash
SCENARIO_PATH="$PWD/packages/game-engine/content/scenarios/my-scenario.json" pnpm dev:api
```

В Docker файл можно подключить без пересборки образа:

```bash
docker run --rm -p 8787:8787 \
  -e SCENARIO_PATH=/config/scenario.json \
  -v "$PWD/my-scenario.json:/config/scenario.json:ro" \
  -v ai-sdlc-data:/data ai-sdlc-api
```

После изменения внешнего файла перезапустите API. Новые комнаты получат новый сценарий, а уже
созданные продолжат использовать сохранённый в SQLite снимок.
