# AI SDLC RPG: архитектура MVP

## Выбор стека

Рассматривались два варианта.

| Вариант | Сильная сторона | Цена для этого MVP |
| --- | --- | --- |
| React + Vite, FastAPI, SQLAlchemy | Зрелый API-стек и удобная работа с SQLite | Контракты и игровая модель живут в двух языках; нужен отдельный шаг генерации типов |
| TypeScript-монорепозиторий: React + Vite, Fastify, SQLite | Один набор типов, простой общий контракт и чистый движок без зависимости от сервера | Нужно аккуратно отделить доменную логику от HTTP и базы |

Для MVP выбран **TypeScript-монорепозиторий**. Главный аргумент — игровой движок остаётся чистой библиотекой, а типы состояния и команд общие для API и интерфейсов. Это сокращает количество связующего кода в первом сквозном срезе.

Заготовка Vinext/Sites заменяется обычным Vite-приложением. Она рассчитана на Cloudflare Workers и публикацию через Sites, а здесь фронтент должен быть статическим GitHub Pages-сайтом, который обращается к отдельно развёрнутому API.

## Структура

```text
apps/
  web/             React, Vite, HashRouter; экраны ведущего, игрока и зала
  api/             Fastify, HTTP, WebSocket, SQLite, транзакции
packages/
  contracts/       общие типы состояния, команд и ответов API
  game-engine/     сценарий, расчёт эффектов, события, победа и поражение
docs/              правила и архитектура
```

Сервер — единственный источник правды. Браузер показывает состояние и отправляет намерение: голос или команду ведущего. Все проверки переходов и расчёты выполняются на сервере.

## Состояния игры

```text
LOBBY → VOTING → RESULT → EVENT → FEEDBACK → VOTING
                                             ↘ WON
                                             ↘ BROKEN
```

- `LOBBY`: игроки входят, ведущий готовит первый раунд.
- `VOTING`: голос можно отдать или заменить.
- `RESULT`: голосование закрыто, победитель зафиксирован. При ничьей нужен выбор ведущего из лидеров.
- `EVENT`: событие показано залу, но его эффект ещё не применён.
- `FEEDBACK`: последствия применены, можно обсудить обновлённую карту и перейти дальше.
- `WON`: выполнено правило победы.
- `BROKEN`: показатель стал критическим или после последнего раунда не выполнено правило внедрения.

Команды ведущего передают ожидаемую версию перехода. `transitionVersion` меняется только после админской команды, а `revision` — после любой мутации, включая вход и голос. Поэтому новый голос не делает кнопку ведущего устаревшей. Переход и увеличение обоих счётчиков выполняются в одной короткой транзакции. Устаревшая команда получает конфликт `409` и новое состояние.

## HTTP и WebSocket

Минимальный API:

- `POST /api/games` — создать игру и один раз получить секрет ведущего;
- `POST /api/games/:code/join` — войти по коду и получить токен игрока;
- `GET /api/games/:code/state` — получить полное состояние; с токеном игрока ответ также содержит его текущий голос;
- `PUT /api/games/:code/vote` — отдать или заменить голос;
- `POST /api/games/:code/admin/commands` — выполнить допустимую команду ведущего;
- `GET /health` — проверить API и базу;
- `GET /api/games/:code/ws` — подписаться на уведомления об изменении версии.

WebSocket не переносит частичные патчи. Он сообщает, что появилась новая `revision`, после чего клиент забирает полное состояние по HTTP. Несколько быстрых уведомлений объединяются в одно чтение. После обрыва клиент переподключается с задержкой и также перечитывает состояние. Запоздалый HTTP-ответ не может заменить более новую ревизию. Поэтому потерянное сообщение не ломает синхронизацию.

## Данные

SQLite хранит:

- `games` — код, фаза, версия, показатели, свойства, карта этапов, конфигурация и секрет ведущего в виде хеша;
- `players` — имя, токен в виде хеша и время входа;
- `game_rounds` — снимок ситуации и события каждого раунда;
- `round_options` — четыре варианта и их игровые эффекты;
- `votes` — один текущий голос игрока на раунд, заменяемый через upsert;
- `action_log` — входы, смены голосов и команды ведущего; рассчитанный план последствий хранится вместе с раундом.

Определение сценария копируется в игру при создании. Уже начатая сессия не меняется, если позже поправить сценарий в коде.

SQLite работает в режиме WAL, с `foreign_keys`, `busy_timeout` и короткими транзакциями `BEGIN IMMEDIATE`. Поддерживается один процесс API и постоянный диск. Для резервной копии нужен периодический снимок через SQLite backup API. Если у облака нет постоянного диска или нужны несколько реплик, хранилище надо заменить на PostgreSQL.

## Безопасность и публикация

- Во фронтенте нет заранее заданного секрета ведущего. Секрет создаётся сервером для конкретной игры и хранится только в сессии браузера ведущего.
- Токен игрока также создаётся сервером и позволяет менять только его голос.
- Для production API задаётся точный список разрешённых origin. Запросы с других сайтов отклоняются.
- GitHub Pages собирает только `apps/web`. Используются `HashRouter`, настраиваемый `base` и публичный `VITE_API_BASE_URL`.
- Production-страница и API должны работать по HTTPS; WebSocket — по WSS.
- Docker-образ запускает один экземпляр API и монтирует каталог с SQLite на постоянный диск.

## Проверки первого среза

Узкие автоматические тесты покрывают:

- детерминированный расчёт решения, события и защитного свойства;
- критический порог и финальное правило победы;
- смену голоса одним игроком;
- восстановление личного голоса по токену без раскрытия его в публичном состоянии;
- отсутствие скрытых численных эффектов в публичном описании вариантов;
- запрет голоса после закрытия;
- ничью и выбор только из лидирующих вариантов;
- версионный конфликт команды ведущего;
- восстановление состояния из SQLite после повторного открытия базы.

## Что остаётся до боевого использования

- откалибровать пять раундов на репетиции;
- выбрать облако API, настроить постоянный диск, резервные копии и секреты;
- указать реальные адреса Pages и API в CORS и переменных сборки;
- проверить мобильные устройства и экран зала в реальной сети;
- после отдельного разрешения создать удалённый репозиторий и включить публикацию.
